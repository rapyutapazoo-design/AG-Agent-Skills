# 07 auto-flow 段階2: 仕様の検証(小実験)

## 目的

段階3(ガードの移植)に進む前に、**公式ドキュメントに記載が無かった6項目**を、使い捨てのサンプル環境で確かめます。結果は表にまとめさせ、私(Claude)に貼っていただければ、段階3の指示書を結果に合わせて調整します。

| # | 検証項目 | 結果が影響すること |
|---|---|---|
| 1 | サブエージェント内のツール呼び出しで、`BeforeTool` フックが発火するか | 層2ガード(禁止コマンドの拒否)がサブエージェントに効くか |
| 2 | `BeforeAgent` フックから、モデル側へ情報(トークン・セッションID)を渡せるか。環境変数にセッションIDがあるか | 起動認可の方式(自動マージを解禁する場合のみ必要) |
| 3 | `session_id` が、同一セッションの複数ターンおよびサブエージェント呼び出しで同じか | 同上 |
| 4 | `settings.json` に常時登録したフックが、対象外の操作を素通りさせられるか | ガードの常時登録の安全性 |
| 5 | OS、シェル、Python の有無、フックのコマンド文字列の解釈(`$HOME`・クォート) | Windows 対応の要否と書き方 |
| 6 | メインのエージェントがサブエージェントを確実に呼べるか(自動委譲、`@名前`)と、`model` 指定が効くか | auto-flow の各フェーズの呼び出し方 |

前提: 段階1(06)の実行が済んでいること。**この検証は、実在のプロジェクトでは行いません。**

## ▼ コピペ用プロンプト

~~~~
auto-flow の移植に必要な仕様を確かめるため、使い捨ての環境で小さな実験を6つ行い、結果を報告してください。以下の安全策を必ず守ってください。

【安全策】
1. 実験は、新規に作る空の一時ディレクトリ（例: `mktemp -d`。Windows では `$env:TEMP` 以下に新規作成）の中だけで行う。このリポジトリや、ほかのプロジェクトのファイルは変更しない
2. フックの設定は、**一時ディレクトリ内のプロジェクト設定（`.gemini/settings.json`）にだけ書く**。グローバルの設定ファイル（`~/.gemini/settings.json` など）は変更しない。もし環境上、グローバルにしか書けない場合は、そこで止めて理由を報告し、私に確認する
3. 実験用のフックスクリプトは、受け取った入力を一時ディレクトリ内のログファイルに追記するだけにする。ネットワーク通信、ファイル削除、ほかのディレクトリへの書き込みはしない
4. 実験用のサブエージェント定義は、一時ディレクトリ内のプロジェクト設定の置き場（`.gemini/agents/`）にだけ作る
5. 実験の最後に、作成した一時ディレクトリを削除し、削除したことを報告する。ログの内容は報告書に転記してから消す
6. 実行できない実験（権限や仕様の問題）は、無理に回避せず「実行できなかった」と理由を報告する

【事前確認】
- OS、シェル（PowerShell／bash／zsh など）、`python3`／`python` の有無とバージョン、`git` のバージョン
- 実行環境が Gemini CLI か Antigravity（IDE／CLI）か。フックの設定ファイルの場所と形式（Gemini CLI は `settings.json` の `hooks`。Antigravity が別の仕組みなら、その仕組み）。ドキュメントで確認できる範囲を報告する

【実験1: サブエージェント内で BeforeTool が発火するか】
1. `.gemini/agents/af-probe.md` を作る（`tools` はコマンド実行ツールと読み取りツール、本文は「依頼されたら `echo probe` を実行して結果を返す」）
2. `BeforeTool` フックを、コマンド実行ツールを対象に登録する。スクリプトは stdin の JSON 全文を `hook.log` に追記し、何も出力せず終了コード0で終わる
3. まず本体のエージェントに `echo main` を実行させ、ログに記録されることを確認する
4. 次に `@af-probe echo probe を実行してください` で、サブエージェント経由でコマンドを実行させる
5. 報告: ログに `probe` の呼び出しが記録されたか。記録された場合、入力 JSON にサブエージェントを識別できる項目があるか

【実験2: BeforeAgent からの情報受け渡しと環境変数】
1. `BeforeAgent` フックを登録する。スクリプトは stdin の JSON 全文を `hook.log` に追記し、標準出力に「追加コンテキストとして `PROBE_TOKEN=abc123` をモデルに渡す」ための JSON を出力する（ドキュメントで確認できる出力形式を使う。形式が不明なら、確認できた範囲を報告して実験を止める）
2. 「`PROBE_TOKEN` の値は何ですか？」と質問し、モデルがその値を答えられるかを確認する
3. コマンド実行ツールで環境変数一覧を出力し、`session`／`gemini`／`agent`（大文字小文字を区別しない）を含む名前を報告する。**値のうち、認証情報や鍵に見えるものは報告に含めない（名前だけ）**
4. 報告: 受け渡しができたか、その出力形式。セッションIDを表す環境変数があるか

【実験3: session_id の安定性】
1. 実験2のログから、同一セッションで2回以上プロンプトを送り、`session_id` が同じかを確認する
2. 実験1の `probe` の呼び出しの `session_id` が、本体と同じかを確認する
3. 報告: 同じ／違うの別と、違う場合はどの条件で変わるか

【実験4: 常時登録のフックが対象外を素通りできるか】
1. `BeforeTool` フックを1つ作る。スクリプトは、一時ディレクトリに `guard.on` というファイルが存在する場合だけ、コマンドに `FORBIDDEN_WORD` を含むものを拒否する（終了コード2または `decision: "deny"`、ドキュメントで確認できる方式）。`guard.on` が無ければ何もせず終了コード0
2. `guard.on` が無い状態で `echo FORBIDDEN_WORD` を実行させ、通ることを確認する
3. `guard.on` を作り、同じコマンドが拒否されることを確認する。拒否されたときの、モデルへの見え方（エラー文面）を報告する
4. 報告: 拒否の方式（終了コード2／deny）のどちらが効いたか。フックの入力 JSON で、コマンド文字列が入っている項目の名前

【実験5: 環境差】
1. 実験1〜4で使ったフックのコマンド文字列に、ホームディレクトリの参照（`$HOME`、`~`、`%USERPROFILE%`、`$env:USERPROFILE` のいずれか）と、引用符つきのパスを含めて、実際に展開されて動くかを確認する
2. 報告: 動いた書き方、動かなかった書き方。フックのコマンドはどのシェルで解釈されているか

【実験6: サブエージェントの呼び出し】
1. 実験1の `af-probe` と同様に、`description` が明確な読み取り専用のサブエージェント `af-probe-ro`（`tools` は読み取りのみ、`model` を明示）を作る
2. 「この一時ディレクトリのファイル一覧を調べてください」と、サブエージェント名を出さずに依頼し、自動委譲されるかを確認する
3. `@af-probe-ro` で明示して依頼し、委譲されるかを確認する
4. `af-probe-ro` に「書き込みを試みる」依頼をして、`tools` の制限により拒否されるかを確認する（一時ディレクトリ内のみ）
5. `model` の指定が効いているかは、サブエージェントに「あなたのモデル名を答えて」と尋ねて確認する（答えられなければ「確認できなかった」とする）
6. 報告: 自動委譲の可否、`@名前` の可否、`tools` 制限の効き、`model` の効き

最後に、この報告をそのまま私が別の AI に貼れるよう、Markdown の1つのコードブロックにまとめて出力してください。

## 結果の使い方

出力された報告を私(Claude)に貼ってください。結果に応じて、段階3(08)を次のように調整します。

- 実験1が「発火しない」→ 層2(禁止コマンドの拒否)は、サブエージェントでは当てにせず、Git フック層(層1)とサブエージェントの `tools` 制限を主な防御にします
- 実験2・3が「できない」→ 起動認可は移植せず、自動マージは解禁しない(PR 止め固定を維持)
- 実験5で Windows の問題が出た場合 → フックのコマンドを Python 呼び出しに統一するなどの書き換えを指示書に追加します
- 実験6で自動委譲が不確実 → 06 の呼び出し方(`@名前` の明示)を調整します
